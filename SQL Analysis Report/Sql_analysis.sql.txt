
CashLag — SQL Analysis Notes
How I went from raw data to the actual reason payments were late
Report by Yash Kumar

-------------------------------------------------------------------------------------------------------------------------------------

About This Project

This analysis is built on an accounts receivable dataset — 2,466 invoices across 5 regions, tracking whether payments came in on time
or late, whether they were disputed, and whether they were billed on paper or electronically. The goal was simple: figure out why so many
payments were coming in late, and whether there's an actual, fixable reason behind it rather than just "customers are slow."
Everything below is the actual sequence I went through — including the couple of times I got it wrong before I got it right.

-----------------------------------------------------------------------------------

Step 0: Cleaning the data first

Before I touched any analysis, I looked at the raw file and the Region column was a mess — some rows had "REGION A",
some had "region_a", some had extra spaces like " Region B ". If I grouped by Region without fixing this,
the same region would get split into 4-5 fake categories. So this had to be fixed first.

CREATE OR REPLACE TABLE credit_pay_dataset.credit_pay_clean AS
SELECT
CountryCode,
INITCAP(
TRIM(
REPLACE(REPLACE(LOWER(Region), '_', ' '), '-', ' ')
)
) AS Region,
CustomerID,
PaperlessDate,
InvoiceNumber,
InvoiceDate,
DueDate,
InvoiceAmount,
Disputed,
SettledDate,
PaperlessBill,
DaysToSettle,
DaysLate
FROM credit_pay_dataset.credit_pay_raw

This lowercases everything first, replaces underscores and hyphens with spaces, trims extra spaces,
then capitalizes the first letter properly. CREATE OR REPLACE TABLE actually builds this out as a
new table — credit_pay_dataset.credit_pay_clean — and every query after this point runs on that clean table, not the raw one.

Step 1: Which region is actually the slowest?

The first thing I wanted to know was simple — is there even a real difference between regions, or is delay just random across the board.

select
Region,
round(avg(DaysLate), 2) as Avg_delay_days
from
credit_pay_dataset.credit_pay_clean
group by 1
order by 2 desc;

Region C came out worst at 4.82 days average delay, then B (3.94), E (3.64), D (3.61), and Region
A was way better at just 1.85 days. So yes, there's a real gap here — now I needed to know why.

Step 2: My first guess — is it disputes?

My instinct was that disputes were driving the delay, so I checked raw counts of late payments split by disputed vs not disputed, per region.

select
Region,
sum(case when Disputed is true then 1 else 0 end) as late_pays_when_disputed,
sum(case when Disputed is false then 1 else 0 end) as late_pays_when_no_disputed
from
credit_pay_dataset.credit_pay_clean
where DaysLate > 0
group by 1
order by 2 desc;

This is where I got it wrong the first time. Region B showed more disputed late-pays than non-disputed, but Region E showed the
opposite — more non-disputed late-pays. Based on this I assumed dispute wasn't a real factor in regions like A, D, and E.

The problem was I was comparing raw counts, and each region has a different total number of 
disputed vs non-disputed invoices to begin with, so raw numbers don't tell you the real rate.

Step 3: Fixing it — comparing rates instead of raw counts

So I redid it properly, calculating the percentage of late payments within disputed invoices and within non-disputed invoices, separately for each region.

select
Region,
round(sum(case when Disputed is true and DaysLate > 0 then 1 else 0 end) * 100.0 /
sum(case when Disputed is true then 1 else 0 end), 1) as pct_disputed_late,
round(sum(case when Disputed is false and DaysLate > 0 then 1 else 0 end) * 100.0 /
sum(case when Disputed is false then 1 else 0 end), 1) as pct_nondisputed_late
from credit_pay_dataset.credit_pay_clean
group by 1
order by 2 desc;

This is where the real pattern showed up. Every single region had a disputed late-rate 2-3.5x higher
than the non-disputed rate — Region E (81.3% vs 30.8%), Region A (72.1% vs 20.4%), Region C (70.5% vs 23.1%),
Region D (67.8% vs 27.0%), Region B (60.8% vs 29.8%). My first hypothesis was wrong — dispute wasn't limited to a couple of regions,
it was consistent everywhere. Comparing raw counts had completely hidden that.

Step 4: Making sure it's not just one difficult customer

Before trusting this pattern, I wanted to rule out one thing — what if a handful of problem customers were skewing the whole dispute number.

select
CustomerID,
sum(case when Disputed is true then 1 else 0 end) as disputed_count
from
credit_pay_dataset.credit_pay_clean
group by 1
order by 2 desc

The top customer only had 27 disputes, and it dropped off gradually from there (25, 24, 24, 23...).
No single customer was driving this — the disputes were spread across a lot of customers,
which means it's a process problem, not a "one difficult client" problem.

Step 5: Does the length of delay matter?

Next question — does it matter if a payment is a little late versus very late? I bucketed invoices by how many days late they were.

with bucket as (
select ,
case
when DaysLate = 0 then "on time"
when DaysLate between 1 and 15 then "1 to 15 days late"
when DaysLate between 16 and 30 then "16 to 30 days late"
else "30+ days late"
end as aging_bucket
from credit_pay_dataset.credit_pay_clean
)
select
aging_bucket,
count() as payments_count,
sum(case when Disputed is true then 1 else 0 end) as disputed_count,
round(sum(case when Disputed is true then 1 else 0 end) * 100 / count(*), 1) as pct_disputed
from bucket
group by 1

This turned out to be the strongest finding in the whole analysis. On-time payments were only 11.2% disputed,
 1-15 days late was 36.6%, 16-30 days was 71.7%, and 30+ days late was 87.5% disputed. The longer the delay,
 the more likely dispute is the reason — almost a straight line. Worth noting the 30+ day bucket only had 8 invoices total,
 so that exact number is a small sample, but the trend direction is very clear even without it.

Step 6: Does invoice size matter?

I also wanted to check if bigger invoices took longer to settle. First I checked the range.

select
min(InvoiceAmount) as min_invoice_amount,
max(InvoiceAmount) as max_invoice_amount
from
credit_pay_dataset.credit_pay_clean

Range was $5.26 to $128.28. I split that into three buckets.

with level as (
select
,
case
when InvoiceAmount between 0 and 45 then "low_amount"
when InvoiceAmount between 45.01 and 85 then "medium_amount"
when InvoiceAmount between 85.01 and 130 then "high_amount"
end as amount_level
from
credit_pay_dataset.credit_pay_clean
)
select
amount_level,
round(avg(DaysToSettle), 1) as days_to_settle,
sum(case when Disputed is true then 1 else 0 end) as disputed_count,
round(sum(case when Disputed is true then 1 else 0 end) * 100.0 / count(), 1) as pct_disputed
from
level
group by amount_level

Days to settle was almost identical across all three buckets (26.1, 26.2, 28.9) — amount doesn't really affect how long settlement takes.
Dispute percent did creep up a bit with amount (16.0% to 23.0% to 35.6%), but nowhere near as strong as the region or aging-bucket pattern.
Conclusion — invoice amount is a weak factor at best, not a main driver.

Step 7: Paper vs Electronic billing

This one felt like a practical, fixable factor — does the billing method itself change how fast people pay.

select
PaperlessBill,
count() as late_pays,
sum(case when Disputed is true then 1 else 0 end) as disputed_count,
round(sum(case when Disputed is true then 1 else 0 end) * 100.0 / count(), 1) as pct_disputed
from
credit_pay_dataset.credit_pay_clean
where DaysLate > 0
group by 1

I also checked the total invoice count per group to make sure the comparison was fair.

select
PaperlessBill,
count(*) as invoice_count
from
credit_pay_dataset.credit_pay_clean
group by 1

Paper and Electronic had almost the same total invoice count (1263 vs 1203), so a direct comparison was fine here.
Paper invoices were late 43.2% of the time, Electronic only 27.5% — a genuine 15.7 percentage point gap.
Dispute percent was similar in both (Paper 41.9%, Electronic 46.5%), meaning this gap wasn't about disputes
— it was a real billing-format effect on its own. Likely because electronic invoices come with automated reminders and paper ones don't.

Step 8: A hypothesis that didn't hold up

One more idea — maybe payments due near month-end are more likely to be late, since that's when people's own cash might be tighter.

select
case
when EXTRACT(DAY FROM DueDate) >= 25 then "Month End (25-31)"
else "Not Month End"
end as due_date_type,
count() as total_invoices,
sum(case when DaysLate > 0 then 1 else 0 end) as late_count,
round(sum(case when DaysLate > 0 then 1 else 0 end) * 100.0 / count(), 1) as pct_late
from credit_pay_dataset.credit_pay_clean
group by 1

35.8% versus 34.6% — basically no difference. This hypothesis didn't hold up, and that's still worth mentioning,
because it shows the delay isn't about when the due date falls on the calendar — it's about dispute handling and billing format, not timing.

What this all adds up to

Region matters, but it's a symptom, not a cause.

Dispute is the strongest, most consistent driver — the longer a payment is late, the more likely it's tied to a dispute.

It's not one difficult customer — disputes are spread across the customer base, so it's a process issue.

Invoice amount barely matters.

Billing method, Paper versus Electronic, has a real, independent effect — about 15.7 percentage points.

Due date timing, month-end or not, has no effect.

Where this leads: fixing dispute resolution speed and pushing the remaining Paper customers to Electronic billing are the two moves that actually move the needle here.
